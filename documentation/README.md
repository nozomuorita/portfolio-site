# ポートフォリオサイト開発ドキュメント

最終更新日: 2026-09-21

## 結論

このサイトには、大規模な業務システム向けの要件定義書や詳細設計書一式は不要です。一方で、刷新の目的、掲載内容、画面ごとの振る舞い、公開方法を決めずに改修を続けると、デザインや実装の判断がぶれます。

そこで、実際の開発と保守に必要な情報だけを、次の4文書に分けています。

| 文書 | 役割 | 主な読者 |
| --- | --- | --- |
| [01-product-requirements.md](01-product-requirements.md) | 何のために、何を作るかを決める | サイト所有者、開発者 |
| [02-screen-design.md](02-screen-design.md) | 何を、どの順番・見た目・操作で表示するかを決める | デザイナー、開発者 |
| [03-technical-and-aws-design.md](03-technical-and-aws-design.md) | Reactの構成、品質基準、AWS公開方式を決める | 開発者、運用者 |
| [04-github-pages-ci-cd.md](04-github-pages-ci-cd.md) | 現在のGitHub Pages自動デプロイ構成と運用方法を説明する | 開発者、運用者 |

この `README` は文書全体の運用ルールを兼ねます。そのため、独立した「文書管理規定」は作りません。

## 文書の位置づけ

- `01` は軽量な要件定義書です。契約、組織権限、複雑な業務フローは扱いません。
- `02` は画面設計書です。単一ページなので、画面一覧と各セクション仕様を1文書に集約します。
- `03` は基本設計書と運用設計書を兼ねます。小規模サイトのため、コンポーネント単位の詳細設計書はソースコードで代替します。
- `04` はGitHub Pages用CI/CDの詳細設計書兼運用手順書です。ワークフローの意図、旧方式からの変更、障害対応を記録します。
- テスト仕様は各文書の受入条件・確認項目に含めます。現段階では独立したテスト仕様書を作りません。

## 現状と目標の表記

各文書では、次の表記を使用します。

| 表記 | 意味 |
| --- | --- |
| **現状** | 2026-09-21時点でソースコードから確認できた状態 |
| **目標** | 今後実現する正式仕様 |
| **候補** | 方針決定後に採用する案 |
| **対象外** | 今回のサイト刷新では実施しない内容 |

## 更新ルール

1. 掲載内容や画面構成を変える場合は、先に `01` と `02` の該当箇所を更新します。
2. ライブラリ、ビルド方法、AWS構成を変える場合は `03` を更新します。
3. GitHub Pagesのワークフロー、実行条件、Node.js、Actionsのバージョン、運用手順を変える場合は `04` を更新します。
4. 実装と文書が食い違った場合は、「現状」をコードに合わせたうえで「目標」と差分を残します。
5. 未決事項が決まったら、各文書の判断待ち一覧から削除し、正式仕様へ反映します。

## 今後追加するとよい文書

次の文書は、必要になった段階で追加します。先に作る必要はありません。

- AWS構築開始時: IaC（Infrastructure as Code。構成をコードで管理する方法）のREADME

- Contact機能を実装するとき: API仕様、迷惑送信対策、個人情報の取扱方針
- コンテンツ更新を第三者へ依頼するとき: 更新手順書
